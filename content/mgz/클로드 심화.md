# 클로드 심화

![[attachments/image 32.png]]

각 컴포넌트를 클릭하면 더 자세한 설명을 볼 수 있어요. 흐름을 요약하면:

1. **Consumer VPC** — EC2가 `vpce-xxx` DNS 주소로 curl 요청
2. **VPC Endpoint (ENI)** — Private IP로 요청을 받아 AWS 내부망으로 전달
3. **AWS 내부망** — 인터넷을 거치지 않고 Provider VPC로 라우팅
4. **Endpoint Service → NLB → EC2 B** — 순서대로 트래픽 전달 후 응답 반환

Consumer EC2가 VPC Endpoint로 요청을 보내는 방법은?

오후 5:34

Consumer EC2에서 VPC Endpoint로 요청을 보내는 방법은 크게 두 가지입니다.

**DNS로 자동 라우팅 (가장 일반적)**

VPC Interface Endpoint를 생성하면 AWS가 자동으로 DNS 이름을 발급합니다. EC2는 그냥 그 DNS 주소로 평범하게 요청하면 됩니다.

bash

`curl http://vpce-xxxx.vpce-svc-xxxx.ap-northeast-2.vpce.amazonaws.com`

EC2 입장에서는 그냥 HTTP 요청이고, 내부적으로 DNS가 ENI의 Private IP로 해석되어 인터넷을 전혀 거치지 않고 전달됩니다.

**Private DNS 활성화 시 (더 깔끔한 방법)**

Endpoint 생성 시 "Private DNS 활성화" 옵션을 켜면, 서비스 제공자가 커스텀 도메인(예: `api.myservice.internal`)을 등록해 둔 경우 그 도메인 그대로 사용할 수 있습니다. EC2 코드 변경 없이 기존 도메인을 그대로 씁니다.

**필요한 사전 조건**

EC2가 요청을 보내려면 아래 세 가지가 갖춰져 있어야 합니다.

- VPC 설정에서 `enableDnsSupport`, `enableDnsHostnames` 모두 `true`
- EC2의 Security Group → Endpoint ENI 포트(예: 80/443) 아웃바운드 허용
- Endpoint의 Security Group → EC2 인바운드 허용

이 조건이 맞으면 EC2는 별도 게이트웨이나 NAT 없이 Private IP 통신만으로 Provider의 API를 호출할 수 있습니다.

VPC Interface Endpoint란 무엇인가요?

오후 5:35

VPC Interface Endpoint는 AWS PrivateLink 기술을 기반으로 한 네트워크 인터페이스입니다.

**한 줄 정의**

VPC 안에 ENI(Elastic Network Interface)를 생성해서, 인터넷을 거치지 않고 외부 서비스에 Private IP로 직접 연결하는 진입점입니다.

**일반 연결 vs Interface Endpoint 비교**

![[attachments/image 33.png]]

핵심 차이를 정리하면 이렇습니다.

**일반 연결**은 EC2 → IGW → 인터넷 → 서비스 순으로 트래픽이 공개 인터넷을 탑니다. Public IP가 필요하고 외부 노출 위험이 있습니다.

**Interface Endpoint**는 VPC 안에 ENI(Elastic Network Interface) 하나를 만들어서 Private IP를 부여합니다. EC2가 해당 DNS로 요청하면 ENI → AWS PrivateLink → 서비스로 이어지는 완전한 내부망 경로만 사용합니다. 인터넷 게이트웨이도, Public IP도 전혀 필요 없습니다.

ENI가 결국 Endpoint의 실체이고, 그 IP가 DNS에 등록되어 EC2 입장에서는 그냥 평범한 HTTP 요청처럼 보이는 게 핵심입니다.

VPC Endpoint Service는 어떻게 만드나요?

오후 5:36

Endpoint Service 생성은 크게 3단계입니다.

**1단계 — NLB 먼저 생성**

Endpoint Service는 반드시 NLB(Network Load Balancer)를 앞단에 둬야 합니다. EC2 백엔드를 Target Group으로 등록하고 NLB에 연결합니다.

bash

`# Target Group 생성
aws elbv2 create-target-group \
  --name my-tg \
  --protocol TCP \
  --port 80 \
  --vpc-id vpc-xxxxxx \
  --target-type instance

# NLB 생성
aws elbv2 create-load-balancer \
  --name my-nlb \
  --type network \
  --subnets subnet-xxxxxx`

**2단계 — Endpoint Service 생성**

NLB ARN을 연결해서 Endpoint Service를 만듭니다.

bash

`aws ec2 create-vpc-endpoint-service-configuration \
  --network-load-balancer-arns arn:aws:elasticloadbalancing:... \
  --acceptance-required false`

`acceptance-required false`로 설정하면 소비자가 연결 요청 시 자동 수락됩니다. 승인이 필요하면 `true`로 변경합니다.

**3단계 — 소비자 VPC에서 Endpoint 연결**

생성된 `vpce-svc-xxx` 서비스 이름으로 Interface Endpoint를 만듭니다.

bash

`aws ec2 create-vpc-endpoint \
  --vpc-id vpc-xxxxxx \
  --service-name com.amazonaws.vpce.ap-northeast-2.vpce-svc-xxxx \
  --vpc-endpoint-type Interface \
  --subnet-ids subnet-xxxxxx \
  --security-group-ids sg-xxxxxx`

전체 흐름을 그림으로 보면 이렇습니다.

![[attachments/image 34.png]]

**주의할 점 두 가지**

첫째, NLB와 Endpoint Service는 반드시 같은 리전에 있어야 합니다. 다른 리전끼리는 연결이 되지 않습니다.

둘째, Endpoint Service 생성 후 소비자에게 `vpce-svc-xxx` 서비스 이름을 공유해야 합니다. 소비자는 이 이름으로 Interface Endpoint를 만들어 연결합니다. `acceptance-required true`인 경우 Provider 측에서 연결 요청을 수동으로 수락해줘야 통신이 시작됩니다.

NLB는 왜 필요한가요?

오후 5:36

PrivateLink가 NLB를 요구하는 이유는 구조적인 이유가 있습니다.

**핵심 이유 — PrivateLink는 "단일 진입점"이 필요함**

Interface Endpoint(ENI)는 하나의 IP 주소로 트래픽을 받습니다. 그런데 백엔드 EC2는 여러 대일 수 있고, 장애가 나면 교체도 됩니다. ENI가 EC2에 직접 연결되면 EC2가 바뀔 때마다 Endpoint도 다시 만들어야 합니다. NLB가 그 사이에서 안정적인 단일 고정 주소 역할을 합니다.

![[attachments/image 35.png]]

NLB가 해주는 역할을 정리하면 세 가지입니다.

**고정 엔드포인트 유지** — EC2가 교체되거나 스케일 인/아웃이 일어나도 NLB의 주소는 바뀌지 않습니다. ENI는 NLB만 바라보면 되므로 Endpoint를 재생성할 필요가 없습니다.

**부하 분산** — 여러 EC2에 트래픽을 나눠줍니다. PrivateLink 자체는 로드밸런싱 기능이 없어서 NLB 없이는 단일 EC2에만 연결할 수 있습니다.

**헬스체크** — EC2가 죽으면 NLB가 자동으로 감지해서 해당 인스턴스로의 트래픽을 차단합니다. 소비자 입장에서는 장애를 인식하지 못한 채 정상 서버로만 요청이 전달됩니다.

ALB(Application Load Balancer)는 사용할 수 없는데, PrivateLink가 L4(TCP) 레벨에서 동작하기 때문입니다. ALB는 L7(HTTP)이라 계층이 맞지 않습니다.

EC2 B 백엔드 서버가 응답을 반환하는 방식은?

오후 5:37

EC2 B가 요청을 받고 응답을 돌려보내는 전체 경로를 단계별로 보면 이렇습니다.

![[attachments/image 36.png]]

파란 점선이 요청, 초록 점선이 응답 경로입니다. 중요한 점은 **응답도 동일한 내부망 경로를 역방향으로** 그대로 따라간다는 것입니다.

**EC2 B 입장에서 보면**

EC2 B는 PrivateLink나 ENI의 존재를 전혀 모릅니다. NLB에서 들어오는 일반 TCP 요청으로만 인식합니다. 애플리케이션 코드는 그냥 평범한 HTTP 서버입니다.

python

`# EC2 B에서 실행되는 서버 (단순 Flask 예시)
from flask import Flask, jsonify
import socket

app = Flask(__name__)

@app.route('/')
def hello():
    return jsonify({
        "message": "Hello from Backend API",
        "server": socket.gethostname(),   # → "EC2 B"
        "service": "privatelink-demo"
    })`

**응답이 돌아오는 경로 요약**

EC2 B → NLB → PrivateLink 터널 → ENI → 소비자 EC2 순으로, 요청과 완전히 동일한 경로를 역방향으로 타고 돌아옵니다. 중간에 인터넷 구간이 전혀 없기 때문에 응답 내용이 외부에 노출될 위험이 없습니다.
