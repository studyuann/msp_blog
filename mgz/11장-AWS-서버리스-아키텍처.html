11장 AWS 서버리스 아키텍처

API Gateway, Lambda, SQS, SNS, Kinesis, Step Functions

11.1 서버리스 아키텍처 개요

서버리스 아키텍처는 서버가 아예 없다는 뜻이 아님.

실제로는 서버가 존재하지만, 사용자가 서버를 직접 프로비저닝하거나 운영하지 않아도 되도록 추상화된 실행 방식임.

즉, 서버리스의 핵심은 다음과 같음.

서버를 직접 관리하는 대신,
이벤트와 코드 실행 중심으로 애플리케이션을 구성한다.

기존에는 애플리케이션을 실행하려면 보통 다음을 직접 고민해야 했음.

  • 서버를 몇 대 둘지
  • 운영체제를 어떻게 관리할지
  • 확장을 어떻게 할지
  • 장애 복구를 어떻게 할지
  • 패치를 어떻게 적용할지

반면 서버리스에서는 이런 부분 상당수를 AWS가 관리하고, 사용자는 코드, 이벤트, 흐름에 더 집중할 수 있음.

11.2 서버리스가 필요한 이유

기존 EC2 기반 구조는 강력하고 유연하지만, 항상 서버 운영 부담이 따름.

예를 들어 다음과 같은 요구가 있다고 가정하면

  • 이미지 업로드 시 자동 처리
  • 특정 이벤트 발생 시 알림 발송
  • 요청이 올 때만 짧게 실행되는 API 처리
  • 큐에 쌓인 작업 비동기 처리
  • 여러 단계를 순서대로 실행하는 워크플로우

이런 작업을 위해 항상 서버를 24시간 켜 두는 것은 비효율적일 수 있음.

서버리스가 적합한 이유

1. 이벤트 중심 실행

필요한 순간에만 실행 가능함.

2. 운영 부담 감소

서버 패치, 인프라 관리 부담이 줄어듦.

3. 자동 확장

요청 수에 따라 자동으로 확장될 수 있음.

4. 사용량 기반 과금

항상 서버를 띄워둘 필요가 없는 경우 비용 효율성이 좋아질 수 있음.

즉, 서버리스는 특히 간헐적 요청, 이벤트 처리, 비동기 처리, API 백엔드에 잘 맞음.

11.3 서버리스 아키텍처의 핵심 개념

서버리스 아키텍처를 이해할 때 중요한 관점은 “기능을 서버 단위로 보지 않고, 이벤트와 서비스 조합 단위로 본다”는 점임.

주요 개념

  • Event-driven
  • Managed execution
  • Function-based processing
  • Decoupling
  • Workflow orchestration

즉, 서버리스는 단일 서비스가 아니라 이벤트가 발생하면 필요한 기능이 연결되어 동작하는 구조라고 이해하는 것이 좋음.

11.4 이벤트 기반 아키텍처

서버리스는 이벤트 기반 아키텍처와 매우 잘 맞음.

이벤트란 시스템에서 어떤 일이 발생했다는 사실 자체임.

예

  • 사용자가 API 호출
  • S3에 파일 업로드
  • 큐에 메시지 도착
  • 일정 시간이 도래
  • DB 변경 발생
  • 주문 완료 이벤트 발생

이벤트 기반 아키텍처에서는 이런 사건이 발생했을 때 필요한 후속 작업을 자동으로 연결함.

예시 흐름

사용자 주문 완료
   │
이벤트 발생
   ├ 알림 발송
   ├ 결제 후처리
   ├ 재고 차감
   └ 로그 저장

즉, 서버리스는 기능을 이벤트 반응 단위로 쪼개고 연결하는 데 적합함.

11.5 Amazon Lambda 개요

Lambda는 AWS의 대표적인 서버리스 컴퓨팅 서비스임.

코드를 업로드하면 AWS가 실행 환경을 관리하고, 이벤트가 들어올 때만 코드를 실행함.

즉, Lambda의 핵심은 다음과 같음.

코드를 함수 단위로 실행한다.
서버 운영은 AWS가 관리한다.

사용자는 보통 다음에 집중하면 됨.

  • 어떤 이벤트가 입력되는가
  • 어떤 코드를 실행할 것인가
  • 결과를 어디로 보낼 것인가

Lambda는 서버리스 아키텍처의 실행 엔진 역할을 한다고 보면 됨.

11.6 Lambda의 특징

1. 이벤트 기반 실행

항상 켜져 있는 서버가 아니라, 호출될 때 실행됨.

2. 자동 확장

동시 요청 증가 시 자동으로 확장 가능함.

3. 짧은 작업에 적합

일반적으로 짧고 독립적인 작업에 적합함.

4. 다양한 이벤트 소스 지원

API Gateway, S3, SQS, EventBridge, DynamoDB Streams 등과 연결 가능함.

즉, Lambda는 다른 서버리스 서비스들과 결합될 때 진가가 커짐.

11.7 Lambda가 적합한 경우

  • 간단한 API 백엔드
  • 이미지/파일 처리
  • 이벤트 후처리
  • 로그 처리
  • 비동기 작업 처리
  • 일정 기반 작업
  • 서버리스 워크플로우의 개별 단계

즉, Lambda는 “작고 독립적인 기능” 단위에 잘 맞음.

11.8 Lambda의 한계와 고려사항

1. 장시간 실행 작업에는 부적합할 수 있음

긴 배치 작업이나 지속적 연결이 필요한 작업에는 한계가 있을 수 있음.

2. 상태 저장 부적합

Lambda 자체 실행 환경에 중요한 상태를 두면 안 됨.

3. 콜드 스타트 고려

오랜 시간 사용하지 않은 함수가 처음 실행될 때 초기 지연이 발생할 수 있음.

4. 복잡한 애플리케이션 로직은 구조 설계가 중요함

작은 함수가 많아질수록 전체 흐름 관리가 중요해짐.

즉, Lambda는 강력하지만 모든 워크로드를 Lambda로 해결하려고 하면 오히려 구조가 복잡해질 수 있음.

11.9 Amazon API Gateway 개요

API Gateway는 클라이언트 요청을 받아 백엔드 서비스에 전달하는 관리형 API 프론트도어 서비스임.

쉽게 말하면 다음 역할을 함.

  • 외부 요청 수신
  • 경로/메서드 관리
  • 인증/인가 연계
  • 요청 제한
  • 백엔드 연결
  • 모니터링

즉, API Gateway는 서버리스 아키텍처에서 외부 요청의 진입점 역할을 함.

11.10 API Gateway가 필요한 이유

Lambda를 직접 외부에 공개하는 것이 아니라 API Gateway를 앞단에 두는 이유는 다음과 같음.

1. 표준 API 인터페이스 제공

HTTP/HTTPS 방식으로 외부 요청을 받을 수 있음.

2. 라우팅 관리

경로와 메서드별로 다른 백엔드에 연결 가능함.

3. 인증/인가 연계

IAM, Cognito, Lambda Authorizer 등과 연결 가능함.

4. 운영 기능 제공

Throttling, Logging, Monitoring, Versioning 등을 관리 가능함.

즉, API Gateway는 단순 전달자가 아니라 API 운영 계층임.

11.11 API Gateway의 역할

예를 들어 다음 구조를 생각하면

사용자
   │
API Gateway
   │
Lambda
   │
DynamoDB

API Gateway는

  • 요청을 받아들이고
  • Lambda에 전달하고
  • 응답을 다시 사용자에게 돌려주는

역할을 수행함.

즉, 서버리스 API 구조에서는 ALB 대신 API Gateway가 진입점이 되는 경우가 많음.

11.12 API Gateway가 적합한 경우

  • 모바일 앱 백엔드 API
  • 웹 프론트엔드용 API
  • 서버리스 백엔드 구성
  • 마이크로서비스 API 노출
  • 외부 파트너 API 제공

즉, HTTP API를 서버리스 방식으로 구성할 때 핵심 서비스라고 보면 됨.

11.13 비동기 처리의 필요성

서버리스 아키텍처를 이해할 때 중요한 또 하나의 개념이 비동기 처리임.

모든 작업을 사용자 요청 처리 안에서 즉시 끝내려고 하면 다음 문제가 발생할 수 있음.

  • 응답 시간이 길어짐
  • 실패 영향이 커짐
  • 부하가 집중됨
  • 확장성이 떨어짐

예를 들어 사용자가 주문 버튼을 눌렀을 때 다음 작업이 동시에 일어난다고 가정하면

  • 주문 저장
  • 결제 처리
  • 이메일 발송
  • 문자 발송
  • 재고 차감
  • 로그 분석 이벤트 전송

이 모든 것을 동기적으로 처리하면 응답이 느려질 수 있음.

따라서 핵심 응답과 후속 처리를 분리하는 구조가 필요함.

이때 중요한 서비스가 SQS, SNS, Kinesis 같은 메시징/이벤트 서비스임.

11.14 Amazon SQS 개요

SQS는 Simple Queue Service의 약자이며, 관리형 메시지 큐 서비스임.

메시지를 큐에 저장하고, 소비자가 나중에 꺼내 처리할 수 있게 해줌.

즉, SQS의 핵심은 다음과 같음.

보내는 쪽과 처리하는 쪽을 분리한다.

예를 들어 웹 애플리케이션이 작업 요청을 큐에 넣고, 백엔드 처리기가 나중에 꺼내 처리할 수 있음.

11.15 SQS가 필요한 이유

SQS를 사용하는 이유는 시스템 간 결합도를 낮추기 위해서임.

예를 들어 주문 서비스가 알림 서비스에 직접 의존하면, 알림 서비스 장애가 주문 처리까지 영향을 줄 수 있음.

반면 큐를 중간에 두면 주문 서비스는 메시지만 넣고 빠르게 끝낼 수 있음.

장점

1. Decoupling

생산자와 소비자를 분리할 수 있음.

2. 부하 완충

순간적으로 요청이 몰려도 큐에 저장해 두고 천천히 처리 가능함.

3. 장애 격리

소비자 장애가 생산자 전체를 즉시 중단시키지 않음.

4. 비동기 처리

사용자 응답과 후속 작업을 분리할 수 있음.

즉, SQS는 서버리스에서 안정적인 비동기 처리의 핵심 구성요소임.

11.16 SQS의 주요 개념

SQS를 이해할 때 중요한 개념

  • Queue
  • Message
  • Producer
  • Consumer
  • Visibility Timeout
  • Dead-Letter Queue

11.16.1 Queue

메시지가 쌓이는 저장소임.

11.16.2 Producer

메시지를 보내는 쪽임.

11.16.3 Consumer

메시지를 꺼내 처리하는 쪽임.

11.16.4 Visibility Timeout

소비자가 메시지를 가져간 뒤 일정 시간 동안 다른 소비자에게 안 보이게 하는 시간임.

11.16.5 Dead-Letter Queue

반복 실패한 메시지를 별도로 격리하는 큐임.

즉, SQS는 단순 적재소가 아니라 재시도와 실패 격리까지 고려한 처리 구조를 제공함.

11.17 Standard Queue와 FIFO Queue

SQS는 대표적으로 두 가지 유형이 있음.

Standard Queue

  • 높은 처리량
  • 최소 1회 전달 보장
  • 순서 보장은 엄격하지 않을 수 있음

FIFO Queue

  • 순서 보장
  • 중복 처리 방지 강화
  • 처리량은 상대적으로 제약이 있을 수 있음

즉,

  • 순서가 크게 중요하지 않으면 Standard
  • 순서와 중복 제어가 중요하면 FIFO

로 이해하면 됨.

11.18 Amazon SNS 개요

SNS는 Simple Notification Service의 약자이며, 관리형 pub/sub 메시징 서비스임.

SNS의 핵심은 다음과 같음.

하나의 이벤트를 여러 구독자에게 동시에 전달한다.

즉, SQS가 큐 기반 1차원 적재 구조라면, SNS는 발행-구독(Publish-Subscribe) 구조임.

11.19 SNS가 필요한 이유

같은 이벤트를 여러 시스템이 각각 받아야 하는 경우가 있음.

예

  • 주문 완료
  • 이메일 알림
  • 문자 알림
  • 감사 로그 저장
  • 분석 시스템 이벤트 전송

이런 경우 발행자는 한 번만 이벤트를 발행하고, 여러 구독자가 각자 받아 처리하면 됨.

즉, SNS는 이벤트 팬아웃(fan-out)에 적합함.

11.20 SNS의 특징

1. Pub/Sub 구조

하나의 발행자가 여러 구독자에게 전달 가능함.

2. 다양한 구독 대상

SQS, Lambda, HTTP Endpoint, Email 등과 연계 가능함.

3. 이벤트 전파에 적합

시스템 간 느슨한 결합 구조를 만들기 좋음.

즉, SNS는 “한 번 발생한 이벤트를 여러 방향으로 전달하는 서비스”라고 이해하면 됨.

11.21 SQS와 SNS 차이

이 둘은 자주 함께 쓰이지만 역할이 다름.

항목SQSSNS
구조큐Pub/Sub
목적비동기 작업 적재이벤트 팬아웃
소비 방식보통 한 소비자 흐름여러 구독자 동시 전달
대표 용도작업 처리알림/이벤트 배포

즉,

  • 작업을 나중에 처리하려면 SQS
  • 이벤트를 여러 곳에 뿌리려면 SNS

라고 정리하면 됨.

11.22 SQS와 SNS 조합

실무에서는 SNS와 SQS를 함께 사용하는 경우가 많음.

예

주문 완료 이벤트
   │
SNS Topic
   ├ SQS-알림큐
   ├ SQS-정산큐
   └ SQS-분석큐

이 구조의 장점

  • 이벤트는 한 번 발행
  • 여러 후속 시스템이 독립적으로 소비
  • 각 소비 시스템은 자기 속도로 처리 가능

즉, SNS+SQS 조합은 서버리스 이벤트 아키텍처에서 매우 자주 등장하는 패턴임.

11.23 Amazon Kinesis 개요

Kinesis는 실시간 스트리밍 데이터 수집과 처리에 사용되는 서비스군임.

즉, 메시지를 한 건씩 단순 큐잉하는 것을 넘어, 대량의 연속 데이터 흐름(stream)을 처리하는 데 적합함.

예

  • 로그 스트림
  • 클릭스트림
  • IoT 센서 데이터
  • 실시간 모니터링 데이터
  • 대량 이벤트 수집

즉, Kinesis는 “메시지 큐”보다 실시간 데이터 스트림 처리에 더 초점이 맞춰져 있음.

11.24 Kinesis가 필요한 이유

SQS는 비동기 작업 처리에 매우 좋지만, 대량 연속 데이터 흐름을 시간 순서대로 수집·분석하는 용도로는 한계가 있을 수 있음.

이때 Kinesis가 적합함.

장점

1. 대량 실시간 데이터 수집

지속적으로 발생하는 이벤트를 받아들일 수 있음.

2. 스트리밍 처리

데이터가 들어오는 즉시 소비 가능함.

3. 실시간 분석 연계

분석, 모니터링, 저장 파이프라인과 연결 가능함.

즉, Kinesis는 이벤트 처리 중에서도 스트리밍 데이터 파이프라인에 특화된 서비스임.

11.25 Kinesis 서비스군 개요

Kinesis는 여러 구성요소로 나뉨.

교육에서는 너무 깊게 다루기보다 큰 역할 중심으로 정리하는 것이 좋음.

대표 구성

  • Kinesis Data Streams
  • Kinesis Data Firehose
  • Kinesis Data Analytics

11.25.1 Kinesis Data Streams

실시간 스트리밍 데이터를 수집하고 여러 소비자가 읽을 수 있는 서비스임.

11.25.2 Kinesis Data Firehose

스트리밍 데이터를 S3, OpenSearch, Redshift 등으로 적재하는 데 최적화된 서비스임.

11.25.3 Kinesis Data Analytics

스트리밍 데이터를 실시간 분석하는 데 사용됨.

즉, Kinesis는 수집, 전달, 분석까지 이어지는 실시간 데이터 처리 체계를 구성할 수 있음.

11.26 SQS와 Kinesis 차이

이 둘도 혼동하기 쉬움.

항목SQSKinesis
목적비동기 작업 큐실시간 데이터 스트림
처리 방식메시지 단위 적재/소비연속 스트림 처리
대표 용도작업 분리, decoupling로그/이벤트/실시간 분석
소비 모델큐 소비자 중심스트림 소비자 중심

즉,

  • 업무 작업 분리면 SQS
  • 실시간 대량 데이터 흐름이면 Kinesis

라고 정리하면 됨.

11.27 AWS Step Functions 개요

Step Functions는 여러 작업 단계를 순서와 조건에 따라 연결하는 서버리스 워크플로우 서비스임.

즉, 단순히 Lambda 하나 실행하는 것이 아니라,

여러 Lambda 또는 여러 AWS 서비스 호출을 상태 기반 흐름으로 관리할 수 있게 해줌.

핵심은 다음과 같음.

복잡한 처리 절차를 코드에 하드코딩하지 않고
워크플로우로 분리해서 관리한다.

11.28 Step Functions가 필요한 이유

예를 들어 주문 처리 업무를 생각하면 다음 단계가 있을 수 있음.

  • 주문 검증
  • 결제 승인
  • 재고 차감
  • 배송 요청
  • 알림 발송
  • 실패 시 보상 처리

이 모든 흐름을 하나의 Lambda 안에 넣으면 코드가 매우 복잡해질 수 있음.

또한 어느 단계에서 실패했는지 추적도 어려워짐.

Step Functions를 사용하면

  • 단계별 흐름을 명시적으로 정의 가능
  • 조건 분기 가능
  • 재시도 정책 설정 가능
  • 실패 처리 흐름 정의 가능
  • 상태 추적 가능

즉, Step Functions는 서버리스 환경의 오케스트레이션 계층임.

11.29 Step Functions의 핵심 개념

주요 개념

  • State Machine
  • State
  • Transition
  • Choice
  • Retry / Catch

11.29.1 State Machine

전체 워크플로우 정의 자체임.

11.29.2 State

하나의 처리 단계임.

11.29.3 Transition

다음 단계로 넘어가는 흐름임.

11.29.4 Choice

조건에 따라 분기하는 상태임.

11.29.5 Retry / Catch

실패 재시도와 예외 처리 흐름임.

즉, Step Functions는 “함수 실행”보다는 프로세스 흐름 제어에 초점이 있음.

11.30 Lambda와 Step Functions 차이

항목LambdaStep Functions
역할개별 코드 실행여러 단계 흐름 제어
중심 개념함수워크플로우
적합한 용도단일 작업 처리다단계 프로세스 관리

즉,

  • 실제 작업 수행은 Lambda
  • 작업 순서와 분기는 Step Functions

라고 이해하면 됨.

11.31 서버리스의 데이터 저장 원칙

서버리스 함수 자체는 상태를 오래 보존하는 계층이 아님.

따라서 데이터는 외부 관리형 서비스에 저장하는 것이 일반적임.

예

  • 관계형 데이터 → RDS/Aurora
  • 키-값 상태 → DynamoDB
  • 세션/캐시 → Redis
  • 파일 → S3
  • 비동기 메시지 → SQS
  • 스트리밍 데이터 → Kinesis

즉, 서버리스 아키텍처도 결국은 컴퓨팅과 데이터 계층을 분리해서 설계해야 함.

11.32 서버리스 아키텍처의 장점

1. 운영 부담 감소

서버 관리 책임이 크게 줄어듦.

2. 빠른 개발

인프라보다 기능 구현에 집중하기 쉬움.

3. 자동 확장

요청 기반으로 유연하게 확장 가능함.

4. 이벤트 기반 구조에 적합

비동기 처리와 느슨한 결합을 설계하기 좋음.

5. 사용량 기반 비용 구조

간헐적 요청 워크로드에 유리할 수 있음.

즉, 서버리스는 작고 독립적인 기능의 조합에서 큰 장점을 보임.

11.33 서버리스 아키텍처의 한계

1. 긴 실행 시간, 지속 연결 작업 제약

특정 워크로드는 EC2/컨테이너가 더 적합할 수 있음.

2. 복잡한 흐름 관리 필요

함수가 많아질수록 전체 구조 파악이 어려워질 수 있음.

3. 디버깅과 추적 복잡성

분산 이벤트 기반 구조에서는 추적 체계가 중요함.

4. 서비스 간 제약 이해 필요

동기/비동기, 재시도, 중복 처리, 순서 보장 등을 설계해야 함.

즉, 서버리스는 편하지만 구조를 잘못 잡으면 오히려 시스템 이해가 어려워질 수 있음.

11.34 대표 서버리스 패턴

1. API 백엔드 패턴

Client → API Gateway → Lambda → DynamoDB

2. 비동기 작업 처리 패턴

App → SQS → Lambda

3. 이벤트 팬아웃 패턴

Event → SNS → 여러 SQS/Lambda

4. 파일 처리 패턴

S3 업로드 → Lambda 실행

5. 워크플로우 오케스트레이션 패턴

Step Functions → 여러 Lambda / AWS 서비스

이런 패턴을 함께 보여주면 학생들이 서비스 역할을 더 쉽게 연결할 수 있음.

11.35 서비스 역할 한 번에 정리

Lambda

이벤트가 들어오면 코드를 실행하는 서버리스 컴퓨팅 서비스임.

API Gateway

외부 요청을 받아 서버리스 백엔드로 전달하는 API 진입점임.

SQS

비동기 작업 처리를 위한 메시지 큐 서비스임.

SNS

하나의 이벤트를 여러 구독자에게 전달하는 Pub/Sub 서비스임.

Kinesis

실시간 대량 데이터 스트림을 수집·처리하는 서비스임.

Step Functions

여러 작업 단계를 순서와 조건에 따라 연결하는 워크플로우 서비스임.

11.36 멀티 티어 아키텍처와 서버리스의 연결

기존의 EC2 중심 멀티 티어 구조를 서버리스 관점으로 일부 대체하면 다음처럼 볼 수 있음.

사용자
   │
API Gateway
   │
Lambda
   ├ DynamoDB
   ├ SQS
   ├ SNS
   ├ S3
   └ Step Functions

즉, 웹/앱 계층 일부 또는 전체를 서버리스 방식으로 구성할 수 있음.

특히 이벤트 처리, 비동기 처리, API 백엔드, 후처리 작업은 서버리스로 옮기기 좋음.

11.37 운영 관점의 설계 포인트

1. 동기와 비동기를 구분해야 함

모든 작업을 요청-응답 안에서 끝내려고 하지 않는 것이 중요함.

2. 중복 처리 고려

이벤트 기반 구조에서는 중복 실행에 대비한 설계가 필요함.

3. 실패 처리 설계

재시도, DLQ, Catch, 보상 처리 등을 함께 봐야 함.

4. 상태 저장 분리

Lambda 내부가 아니라 외부 저장소에 상태를 둬야 함.

5. 관찰 가능성 확보

CloudWatch Logs, Metrics, Tracing이 매우 중요함.

즉, 서버리스는 인프라 부담은 줄지만 아키텍처 설계 책임은 여전히 중요함.

11.39 한 줄 정리

Lambda는 코드를 실행한다.
API Gateway는 요청의 진입점이 된다.
SQS는 작업을 비동기화한다.
SNS는 이벤트를 여러 곳으로 전파한다.
Kinesis는 실시간 데이터 흐름을 처리한다.
Step Functions는 여러 단계를 하나의 워크플로우로 연결한다.
