12장 AWS 엣지 아키텍처

Route 53, CloudFront, DDoS 보호, AWS Outposts

12.1 엣지 아키텍처 개요

사용자가 클라우드 서비스를 사용할 때 실제 경험하는 품질은 단순히 백엔드 서버 성능만으로 결정되지 않음.

다음 요소가 함께 영향을 줌.

  • 사용자가 어느 위치에서 접속하는가
  • DNS가 얼마나 빠르고 안정적으로 응답하는가
  • 정적 콘텐츠가 사용자와 얼마나 가까운 곳에서 제공되는가
  • 대규모 공격 상황에서도 서비스가 유지되는가
  • 일부 워크로드를 온프레미스에 가깝게 배치해야 하는가

즉, 엣지 아키텍처는 클라우드 중심부가 아니라 사용자 접점에서의 성능, 가용성, 보안, 지연시간을 다루는 영역임.

AWS에서 이 역할을 대표적으로 담당하는 서비스가 다음과 같음.

  • Route 53
  • CloudFront
  • AWS Shield / WAF
  • AWS Outposts

12.2 엣지 서비스가 필요한 이유

클라우드에 서버를 잘 배치했다고 해도, 사용자는 항상 AWS 리전 내부에 있는 것이 아님.

전 세계 다양한 위치에서 접속하며, 네트워크 경로도 일정하지 않음.

이때 발생할 수 있는 문제

  • DNS 응답 지연
  • 원본 서버까지 장거리 전송으로 인한 느린 응답
  • 대규모 트래픽 공격에 취약
  • 글로벌 사용자에게 동일한 성능 제공 어려움
  • 온프레미스와 유사한 위치에서 처리해야 하는 워크로드 존재

즉, 엣지 서비스는 단순 부가 기능이 아니라 사용자 경험 최적화와 서비스 보호를 위한 핵심 계층임.

12.3 AWS 글로벌 인프라와 엣지

AWS는 리전과 AZ만 있는 것이 아니라, 전 세계에 분산된 엣지 로케이션과 네트워크 인프라를 함께 운영함.

여기서 중요한 개념

  • Region
  • Availability Zone
  • Edge Location

앞에서 리전과 AZ는 학습했으므로, 여기서는 Edge Location의 의미가 중요함.

Edge Location

사용자와 가까운 위치에서 콘텐츠 전달, DNS 응답, 일부 보안 기능 등을 수행하는 글로벌 접점임.

대표적으로 다음 서비스들이 Edge Location을 활용함.

  • CloudFront
  • Route 53
  • AWS Shield 일부 기능

즉, 엣지 아키텍처는 AWS의 글로벌 분산 네트워크를 기반으로 동작함.

12.4 Amazon Route 53 개요

Route 53은 AWS의 관리형 DNS 서비스임.

도메인 이름을 IP 주소나 AWS 리소스와 연결해 주는 역할을 함.

예를 들어 사용자가 브라우저에 다음을 입력한다고 가정하면

www.example.com

실제로는 이 이름을 어느 서버나 서비스로 보낼지 결정해야 함.

그 역할을 DNS가 하며, Route 53은 AWS가 제공하는 DNS 서비스임.

즉, Route 53의 핵심은 다음과 같음.

사용자가 기억하기 쉬운 이름을
실제 서비스 위치와 연결한다.

12.5 DNS가 중요한 이유

DNS는 사용자가 서비스를 이용할 때 거의 항상 가장 먼저 거치는 단계임.

따라서 느리거나 잘못 구성되면 서비스 전체 접근성에 영향을 줌.

DNS가 중요한 이유

1. 서비스 진입점

사용자는 IP보다 도메인 이름으로 접속함.

2. 가용성에 영향

잘못된 DNS 설정은 서비스 장애와 동일한 결과를 만들 수 있음.

3. 트래픽 분산과 장애 조치 가능

DNS 수준에서 여러 대상 중 어디로 보낼지 결정할 수 있음.

즉, DNS는 단순 주소 변환이 아니라 서비스 접근 제어의 출발점임.

12.6 Route 53의 역할

Route 53은 단순 A 레코드 저장소가 아님.

다음 기능들을 제공함.

  • DNS 레코드 관리
  • 도메인 등록
  • 헬스 체크
  • 라우팅 정책 기반 트래픽 분산
  • 장애 조치 라우팅

즉, Route 53은 DNS 서비스이면서 동시에 글로벌 트래픽 제어 서비스의 성격도 가짐.

12.7 Hosted Zone 개념

Route 53에서 중요한 개념 중 하나가 Hosted Zone임.

Hosted Zone은 특정 도메인에 대한 DNS 레코드 집합을 관리하는 논리적 공간임.

예를 들어

example.com

도메인을 관리한다면, 그 안에 다음과 같은 레코드가 들어갈 수 있음.

  • www.example.com
  • api.example.com
  • mail.example.com

즉, Hosted Zone은 도메인 단위 DNS 관리 영역이라고 보면 됨.

12.8 DNS 레코드 기본 개념

Route 53에서는 다양한 레코드를 사용할 수 있음.

대표적으로 다음을 이해하면 됨.

A 레코드

도메인 이름을 IPv4 주소에 매핑함.

AAAA 레코드

도메인 이름을 IPv6 주소에 매핑함.

CNAME 레코드

다른 도메인 이름으로 별칭을 연결함.

MX 레코드

메일 서버를 지정함.

TXT 레코드

도메인 검증, SPF, DKIM 등 부가 정보를 저장함.

즉, DNS는 단순히 웹 접속뿐 아니라 다양한 네트워크 서비스의 주소 체계를 담당함.

12.9 Alias 레코드

AWS Route 53에서는 일반 DNS의 CNAME과 유사하지만 더 AWS 친화적인 Alias 레코드를 지원함.

Alias 레코드는 다음과 같은 AWS 리소스를 대상으로 많이 사용함.

  • CloudFront Distribution
  • ALB
  • S3 Static Website Endpoint
  • API Gateway

장점

  • 루트 도메인(apex domain)에도 활용 가능함
  • AWS 리소스와 자연스럽게 연동됨

즉, AWS 환경에서는 CNAME보다 Alias를 더 자주 보게 됨.

12.10 Route 53 라우팅 정책

Route 53의 중요한 강점 중 하나는 단순 응답이 아니라 정책 기반 라우팅임.

대표적인 정책

  • Simple Routing
  • Weighted Routing
  • Latency Routing
  • Failover Routing
  • Geolocation / Geoproximity Routing
  • Multi-Value Answer Routing

이 장에서는 개념 중심으로 이해하면 충분함.

12.10.1 Simple Routing

가장 기본적인 방식임.

하나의 도메인을 하나의 대상에 연결하는 단순 구조임.

예

  • www.example.com → 하나의 ALB

12.10.2 Weighted Routing

여러 대상에 가중치를 두고 트래픽을 분산함.

예

  • 새 버전 서버 10%
  • 기존 버전 서버 90%

즉, 점진적 전환이나 간단한 실험 구조에 활용 가능함.

12.10.3 Latency Routing

사용자에게 가장 낮은 지연시간이 예상되는 리전으로 트래픽을 보냄.

예

  • 한국 사용자는 서울 리전
  • 미국 동부 사용자는 버지니아 리전

즉, 글로벌 사용자 성능 최적화에 적합함.

12.10.4 Failover Routing

주 대상이 비정상일 때 보조 대상으로 넘기는 방식임.

예

  • Primary ALB 장애 시 Secondary ALB로 전환

즉, DNS 기반 장애 조치 구조에 사용함.

12.10.5 Geolocation Routing

사용자 위치 정보에 따라 다른 대상에 응답함.

예

  • 한국 사용자 → 한국 사이트
  • 일본 사용자 → 일본 사이트
  • 유럽 사용자 → 유럽 사이트

즉, 국가별/지역별 사용자 경험 분리에 적합함.

12.11 Route 53 Health Check

Route 53은 Health Check 기능과 연계해 비정상 대상에 대한 DNS 응답을 제어할 수 있음.

예를 들어 웹 서버가 응답하지 않으면 DNS에서 그 대상을 제외하거나, 보조 대상으로 넘길 수 있음.

즉, Route 53은 DNS 수준에서도 가용성 전략에 참여할 수 있음.

12.12 Amazon CloudFront 개요

CloudFront는 AWS의 CDN(Content Delivery Network) 서비스임.

정적 콘텐츠, 동적 콘텐츠, API 응답 일부를 전 세계 엣지 로케이션을 통해 사용자에게 더 빠르게 전달할 수 있게 해줌.

즉, CloudFront의 핵심은 다음과 같음.

사용자와 가까운 위치에서 콘텐츠를 제공해
지연시간을 줄이고 원본 부하를 낮춘다.

12.13 CDN이 필요한 이유

사용자가 서울 리전에 있는 서버에 접속하는 경우를 생각해보면, 한국 사용자에게는 크게 느리지 않을 수 있음.

하지만 미국이나 유럽 사용자는 훨씬 먼 경로를 거쳐야 할 수 있음.

이때 문제

  • 정적 파일 응답 지연
  • 이미지/영상 다운로드 느림
  • 원본 서버에 요청 집중
  • 전 세계 사용자 경험 불균형

CDN은 이런 문제를 해결하기 위해 사용자와 가까운 위치에 콘텐츠를 캐시함.

즉, CDN은 성능 향상뿐 아니라 원본 서버 보호와 글로벌 사용자 경험 개선에도 중요함.

12.14 CloudFront의 기본 구조

CloudFront를 이해할 때 중요한 개념

  • Distribution
  • Edge Location
  • Origin
  • Cache
  • Behavior

12.14.1 Distribution

CloudFront의 배포 단위임.

어떤 원본을 대상으로 어떤 캐시 정책과 동작 정책을 적용할지 정의한 전체 구성을 의미함.

12.14.2 Origin

CloudFront가 원본 콘텐츠를 가져오는 원천 서버 또는 스토리지임.

대표 예

  • S3 버킷
  • ALB
  • EC2 웹 서버
  • API Gateway

즉, CloudFront는 원본을 대체하는 것이 아니라 원본 앞단에서 콘텐츠를 캐싱하고 전달함.

12.14.3 Edge Location

사용자와 가까운 위치에서 콘텐츠를 제공하는 글로벌 접점임.

CloudFront는 이 위치들에 콘텐츠를 캐싱해 둠.

12.14.4 Cache

사용자가 요청한 콘텐츠를 엣지 위치에 임시 저장해 두는 기능임.

같은 요청이 다시 오면 원본까지 가지 않고 더 빠르게 응답 가능함.

12.14.5 Behavior

어떤 경로 요청에 어떤 Origin, 캐시 정책, 보안 정책을 적용할지를 정하는 설정임.

예

  • /images/* 는 정적 콘텐츠 캐시 최적화
  • /api/* 는 캐시 없이 원본 전달

즉, CloudFront는 경로별로 다르게 동작하도록 설계 가능함.

12.15 CloudFront의 장점

1. 지연시간 감소

사용자 가까운 엣지에서 응답 가능함.

2. 원본 서버 부하 감소

캐시 적중 시 원본 요청이 줄어듦.

3. 글로벌 서비스 품질 향상

전 세계 사용자에게 더 균일한 성능 제공 가능함.

4. 보안 기능 연계

WAF, Shield, HTTPS, OAC/OAI 등과 결합 가능함.

즉, CloudFront는 성능과 보안을 함께 강화하는 서비스임.

12.16 CloudFront와 정적 콘텐츠

CloudFront는 정적 파일 전달에 특히 강함.

대표 대상

  • 이미지
  • CSS
  • JavaScript
  • HTML
  • 동영상 일부
  • 다운로드 파일

정적 콘텐츠는 자주 변경되지 않고 반복 요청되는 경우가 많기 때문에 캐시 효율이 높음.

즉, S3를 원본으로 두고 CloudFront를 앞단에 두는 구조가 매우 자주 사용됨.

12.17 CloudFront와 동적 콘텐츠

CloudFront는 정적 파일뿐 아니라 동적 콘텐츠에도 일부 도움을 줄 수 있음.

다만 동적 콘텐츠는 캐시 여부를 신중히 봐야 함.

예

  • API 응답 일부
  • 로그인 전 공용 페이지
  • 헤더/쿠키 기반 정책 제어

즉, CloudFront는 모든 것을 무조건 캐시하는 서비스가 아니라,

무엇을 캐시하고 무엇은 원본으로 넘길지 정책적으로 결정하는 서비스임.

12.18 S3 + CloudFront 구조

AWS에서 매우 대표적인 엣지 아키텍처 패턴 중 하나임.

사용자
   │
CloudFront
   │
S3 Origin

이 구조의 의미

  • S3는 원본 저장소
  • CloudFront는 글로벌 배포 계층
  • 사용자는 가까운 엣지에서 콘텐츠 수신

이 패턴은 정적 웹사이트, 이미지 배포, 다운로드 파일 배포에서 매우 자주 사용됨.

12.19 CloudFront와 보안

CloudFront는 단순 캐시가 아니라 보안 계층으로도 의미가 있음.

1. HTTPS 종료

TLS 인증서를 연결해 안전한 전송 가능

2. 원본 보호

사용자가 원본 S3나 ALB에 직접 접근하지 않고 CloudFront만 통하게 구성 가능

3. AWS WAF 연계

웹 공격 필터링 가능

4. Shield 연계

DDoS 보호 강화 가능

즉, CloudFront는 성능 가속기이자 보안 게이트웨이 역할도 할 수 있음.

12.20 DDoS 개요

DDoS는 Distributed Denial of Service의 약자이며, 대량의 트래픽을 집중시켜 정상 사용자가 서비스를 이용하지 못하게 만드는 공격 방식임.

예를 들어

  • 대량 HTTP 요청
  • 네트워크 대역폭 소진
  • 연결 요청 폭주

등이 발생할 수 있음.

즉, DDoS는 서비스 성능 저하를 넘어 가용성 자체를 위협하는 공격임.

12.21 왜 DDoS 보호가 중요한가

운영 환경에서는 서비스가 정상 사용자뿐 아니라 악의적 대량 요청에도 견딜 수 있어야 함.

DDoS 보호가 중요한 이유

1. 가용성 유지

서비스가 멈추면 비즈니스 영향이 큼.

2. 네트워크 자원 보호

트래픽 폭주로 대역폭이 고갈될 수 있음.

3. 원본 인프라 보호

백엔드 서버까지 공격이 도달하면 장애가 확대될 수 있음.

즉, DDoS 보호는 보안의 일부이면서 동시에 고가용성 전략의 일부임.

12.22 AWS Shield 개요

AWS Shield는 AWS에서 제공하는 관리형 DDoS 보호 서비스임.

종류

  • Shield Standard
  • Shield Advanced

12.22.1 Shield Standard

기본적으로 AWS 고객에게 제공되는 수준의 DDoS 보호임.

대표적으로 다음 서비스와 연계됨.

  • CloudFront
  • Route 53
  • Global Accelerator
  • ELB 일부

즉, 기본적인 대규모 네트워크/전송 계층 공격에 대한 방어를 자동으로 제공함.

12.22.2 Shield Advanced

보다 강화된 보호, 가시성, 지원 체계를 제공하는 상위 옵션임.

대규모 중요 서비스에서 고려할 수 있음.

즉, Shield Advanced는 기본 보호를 넘어 고급 운영/보호 기능에 초점을 둠.

12.23 AWS WAF 개요

WAF는 Web Application Firewall임.

L7, 즉 애플리케이션 계층에서 HTTP/HTTPS 요청을 검사하고 필터링하는 보안 서비스임.

대표적으로 다음 공격 방어에 유용함.

  • SQL Injection
  • XSS
  • 비정상 봇 요청
  • 특정 패턴 요청 차단
  • 국가/IP 기반 차단
  • 요청 빈도 제한

즉, Shield가 대규모 트래픽 공격 보호에 가깝다면, WAF는 웹 요청 내용 자체를 제어하는 서비스임.

12.24 Shield와 WAF 차이

항목ShieldWAF
주 보호 대상DDoS 대규모 공격웹 요청 패턴 공격
계층주로 네트워크/전송 계층애플리케이션 계층
대표 대상트래픽 폭주SQLi, XSS, 봇, 비정상 요청

즉,

  • 대량 트래픽 보호는 Shield
  • 웹 요청 필터링은 WAF

라고 보면 됨.

12.25 CloudFront + Shield + WAF 조합

엣지 보안 아키텍처에서 매우 중요한 조합임.

사용자
   │
CloudFront
   ├ Shield
   └ WAF
   │
Origin (S3 / ALB / API Gateway)

이 구조의 의미

  • CloudFront : 글로벌 진입점
  • Shield : 대규모 공격 완충
  • WAF : 악성 웹 요청 필터링
  • Origin : 실제 백엔드

즉, 원본 서버를 인터넷에 직접 노출하기보다,

엣지 계층에서 성능과 보안을 함께 처리하는 구조임.

12.26 AWS Outposts 개요

AWS Outposts는 AWS 인프라와 서비스를 온프레미스 또는 고객 사이트에 가까운 위치에 확장해 배치할 수 있게 하는 서비스임.

즉, Outposts는 다음과 같은 개념임.

AWS의 하드웨어와 운영 모델을
고객의 데이터센터나 현장으로 확장한다.

이는 단순 VPN 연결과는 다른 개념임.

온프레미스에 AWS와 유사한 실행 환경 자체를 가져오는 방식에 가까움.

12.27 Outposts가 필요한 이유

다음과 같은 상황에서는 모든 워크로드를 리전에만 두기 어려울 수 있음.

1. 초저지연 요구

공장, 병원, 통신, 실시간 장비 제어 등에서 현장 가까운 위치 처리가 필요할 수 있음.

2. 데이터 지역성 요구

특정 데이터가 현장에 가까이 있어야 하는 요구가 있을 수 있음.

3. 하이브리드 운영

온프레미스 시스템과 매우 밀접하게 연결된 워크로드가 존재할 수 있음.

즉, Outposts는 클라우드를 쓰되 리전 바깥 현장 가까이에서 AWS 운영 모델을 유지하고 싶을 때 의미가 있음.

12.28 Outposts의 특징

1. AWS 일관된 운영 모델

온프레미스 위치에서도 AWS 서비스 방식과 유사한 운영 가능

2. 하이브리드 환경 적합

온프레미스와 클라우드를 자연스럽게 연결 가능

3. 저지연 처리

현장 가까운 위치 처리 가능

즉, Outposts는 “온프레미스냐 클라우드냐”의 이분법보다

클라우드 운영 모델의 확장이라는 관점에서 이해하는 것이 좋음.

12.29 Route 53, CloudFront, Outposts의 관점 차이

이 장의 서비스들은 모두 “사용자와 가까운 쪽”과 관련 있지만 역할이 다름.

서비스핵심 역할
Route 53사용자를 올바른 서비스 진입점으로 안내
CloudFront콘텐츠를 사용자 가까이에서 전달
Shield / WAF사용자 접점에서 공격 방어
OutpostsAWS 실행 환경을 사용자/현장 가까이에 확장

즉,

  • 접속 경로 결정은 Route 53
  • 콘텐츠 전달 가속은 CloudFront
  • 접점 보안 강화는 Shield/WAF
  • 현장 인프라 확장은 Outposts

라고 보면 됨.

12.30 글로벌 아키텍처 관점의 의미

엣지 서비스는 글로벌 아키텍처와 매우 강하게 연결됨.

예를 들어 글로벌 서비스에서는 다음 구조를 자주 고려함.

  • Route 53으로 지역별 사용자 분산
  • CloudFront로 글로벌 콘텐츠 가속
  • WAF/Shield로 전 세계 트래픽 보호
  • 다중 리전 원본 구조 설계
  • 장애 시 DNS 기반 페일오버

즉, 엣지 서비스는 글로벌 트래픽과 멀티 리전 아키텍처의 시작점이 됨.

12.31 멀티 티어 아키텍처와의 연결

앞에서 만든 멀티 티어 구조를 엣지 관점으로 확장하면 다음과 같음.

사용자
   │
Route 53
   │
CloudFront
   ├ Shield / WAF
   │
ALB 또는 S3 Origin
   │
Web / App / Data Tier

이 구조의 의미

  • Route 53 : 도메인 진입점
  • CloudFront : 글로벌 가속 및 캐싱
  • Shield/WAF : 엣지 보안
  • ALB/S3 : 원본
  • Web/App/Data : 실제 백엔드

즉, 엣지 계층은 기존 아키텍처 앞단에 붙어 사용자 경험과 보안을 강화함.

12.32 운영 관점의 설계 포인트

1. 원본을 직접 노출하지 않는 구조가 유리함

CloudFront 앞단 구조로 원본 보호가 쉬워짐.

2. DNS는 단순 이름 매핑이 아님

장애 조치, 지연시간 최적화, 글로벌 분산까지 고려해야 함.

3. 캐시 정책이 중요함

무조건 캐시가 아니라, 어떤 경로를 얼마나 캐시할지 정책이 필요함.

4. 보안은 엣지에서 선제적으로 처리하는 것이 유리함

공격이 원본까지 가기 전에 막는 것이 좋음.

5. 하이브리드 요구가 있으면 Outposts 같은 선택지도 봐야 함

모든 것을 리전 중심으로만 볼 수 없는 경우가 있음.

12.33 서비스 역할 한 번에 정리

Route 53

도메인 이름을 서비스 진입점과 연결하고, 정책 기반 라우팅을 수행한다.

CloudFront

콘텐츠를 엣지 로케이션에 캐시해 사용자 가까이에서 빠르게 전달한다.

AWS Shield

DDoS 공격으로부터 서비스를 보호한다.

AWS WAF

웹 요청을 검사해 애플리케이션 계층 공격을 차단한다.

AWS Outposts

AWS 인프라와 운영 모델을 온프레미스/현장으로 확장한다.
