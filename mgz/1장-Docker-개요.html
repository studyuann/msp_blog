1장. Docker 개요

목표

  • 컨테이너가 왜 등장했는지(VM 한계) 이해한다.
  • Docker가 해결하는 문제(패키징/배포/격리/이식성)를 설명할 수 있다.
  • Docker의 핵심 구성요소(이미지/컨테이너/레지스트리) 관계를 그림 없이도 말로 정리할 수 있다.
  • 컨테이너의 기반 기술인 namespace / cgroup이 “어떤 역할”을 하는지 운영 관점에서 이해한다.

1.2 Docker란 무엇인가

1.2.1 Docker의 정의

Docker는 애플리케이션과 그 실행 환경(라이브러리/설정)을 “이미지(Image)”로 패키징하여 어디서든 동일하게 실행할 수 있게 해주는 컨테이너 플랫폼이다.

  • Docker는 “가상머신”이 아니라 “컨테이너를 관리하는 도구”이다.
  • 컨테이너는 “프로세스 격리 기술”이고, Docker는 그걸 “사용하기 쉽게” 만든 것이다.

1.2.2 Docker가 해결하는 대표 문제:

개발/운영에서 가장 흔한 문제는 다음과 같다.

  • 개발자: “내 로컬에서는 잘 돼요.”
  • 운영자: “운영 서버에서는 안 돼요.”
  • 원인: 라이브러리 버전, 설정파일, OS 패키지, 런타임 차이

Docker는 이를 다음 방식으로 해결한다.

  • 실행 환경을 통째로 이미지로 고정(버전/설정 포함)
  • 운영 서버에서는 그 이미지를 그대로 실행(동일 환경)

1.2.3 Docker의 장점

  • 재현성(Reproducibility): 같은 이미지면 어디서나 같은 결과
  • 이식성(Portability): 서버가 바뀌어도 실행 환경이 변하지 않음
  • 배포 속도: 이미지 pull → container run (빠름) ⇒ 경량
  • 확장성: 컨테이너 단위로 복제/증설이 쉬움
  • 격리성: 서로 다른 앱이 서로 영향을 덜 줌(파일시스템/네트워크/프로세스 격리)

1.2.4 Docker의 한계/주의사항

  • 커널 공유: 리눅스 컨테이너는 리눅스 커널 기능에 의존

    (Windows 컨테이너는 별도의 구조)

  • 보안: VM보다 격리가 약할 수 있어 운영 보안 설정이 중요

  • 상태 저장 앱(Stateful): DB처럼 데이터가 중요한 서비스는 볼륨/백업 설계가 필수

1.3 Docker 아키텍처(구성 요소)

1.3.1 Client ↔ Daemon ↔ Registry

  1. Docker Client
  • 사용자가 입력하는 docker run, docker ps 같은 명령어 도구
  • 실제로 컨테이너를 만드는 건 클라이언트가 아니라 “Daemon”이 함
  1. Docker Daemon(dockerd)
  • 컨테이너 실행/중지/삭제, 이미지 다운로드, 네트워크/볼륨 관리 등 “실제 작업” 담당
  • 백그라운드 서비스(systemd 서비스로 동작)
  1. Docker Registry
  • 이미지를 저장하는 원격 저장소
  • 대표적으로 Docker Hub, 사내 Private Registry, GitHub Container Registry 등

핵심 문장

docker 명령은 “dockerd에 요청”을 보내고, dockerd가 컨테이너/이미지를 관리한다.

1.3.2 Image / Container / Registry 관계

(1) 이미지(Image)

  • 컨테이너를 만들기 위한 “템플릿/설계도”
  • OS 전체가 아니라, 앱 실행에 필요한 파일 시스템 묶음 + 메타데이터
  • 읽기 전용(read-only)으로 생각하면 편함

(2) 컨테이너(Container)

  • 이미지를 기반으로 “실행된 인스턴스”
  • 내부적으로는 격리된 프로세스
  • 컨테이너는 실행되면서 쓰기 가능한 레이어를 하나 더 얹어서 동작

(3) 레지스트리(Registry)

  • 이미지를 공유/배포하기 위한 저장소
  • docker pull은 레지스트리에서 이미지를 내려받는 동작
  • docker push는 내가 만든 이미지를 업로드하는 동작

1.4 Docker는 컨테이너 도구가 아니라 플랫폼이다

Docker는

컨테이너 기술을 기반으로 애플리케이션을 개발, 배포, 실행, 관리할 수 있도록 제공하는 플랫폼이다.

Docker는 단순히 컨테이너를 실행하는 명령어 집합이 아니라

컨테이너 기반 애플리케이션의 전체 수명주기(Lifecycle)를 지원하는 플랫폼이다.

1.4.1 왜 Docker를 “플랫폼”이라고 부르는가?

Docker가 제공하는 영역

Docker는 다음 여러 계층을 통합 제공한다.

영역Docker가 제공하는 기능
실행(Runtime)컨테이너 실행, 격리
빌드(Build)Dockerfile, 이미지 빌드
배포(Distribution)Registry, Image Push/Pull
네트워크(Network)bridge, DNS, 포트 포워딩
스토리지(Storage)Volume, Bind Mount
리소스 관리CPU / Memory 제한
운영 관리로그, 모니터링, 수명주기 관리
오케스트레이션 연계Compose, Kubernetes 연동

👉 이 모든 것을 하나의 흐름으로 묶어 제공

1.4.2 Docker 플랫폼의 구성 요소

Docker 플랫폼은 단일 프로그램이 아니라 여러 컴포넌트가 유기적으로 연결된 생태계다.

1) Docker Engine (핵심 실행부)

  • 컨테이너 실행 주체
  • Linux 커널 기능(namespace, cgroup) 사용
  • 컨테이너 생명주기 관리

👉 플랫폼의 커널 역할

2) Docker CLI (사용자 인터페이스)

  • 사용자가 Docker 플랫폼과 상호작용하는 인터페이스
  • Engine API를 호출하는 클라이언트

👉 플랫폼의 조작 도구

3) Docker Image & Registry

  • 이미지: 실행 가능한 애플리케이션 패키지
  • Registry: 이미지 저장소 (Docker Hub 등)

👉 플랫폼의 유통 구조

4) Docker Compose

  • 멀티 컨테이너 애플리케이션 정의
  • 서비스 단위 실행/종료
  • 선언형 구성(YAML)

👉 플랫폼의 서비스 조합 계층

1.4.3 Docker 플랫폼이 해결하는 근본적인 문제

1) “환경 차이” 문제

전통적인 문제:

  • 개발 환경 OK
  • 운영 환경 FAIL

Docker의 해결:

  • 실행 환경을 이미지로 고정
  • 어디서 실행해도 동일

2) 배포 복잡성 문제

  • 서버마다 설정 다름
  • 설치 절차 복잡
  • 재현 불가

Docker의 해결:

  • 이미지 기반 배포
  • 설치 과정 제거
  • 동일 이미지 재사용

1.5 운영 자동화의 출발점

Docker는 자동 빌드나 자동 복구 기능을 제공하는 도구가 아니다.

대신 애플리케이션과 실행 환경을 하나의 Image로 고정하여

CI/CD와 Kubernetes 같은 자동화 시스템이

동일한 기준으로 동작할 수 있도록 만든다.

👉 Docker는 운영 자동화를 가능하게 하는 기반 플랫폼이다.

1.6 Docker = 컨테이너 + 플랫폼 사고방식

❌ Docker = 컨테이너 실행 도구

⭕ Docker = 컨테이너 기반 애플리케이션 플랫폼
